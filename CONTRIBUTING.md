## Project overview

VSC Adwaita Next is a VS Code theme extension. It contributes eight colour themes
and one product icon theme, and contains no runtime code at all: no activation
events, no `main` entry point, no background processes.

Almost everything in the repository is either

- a **source of truth** (`src/`), which is TypeScript and data, or
- a **generated asset** (`themes/`, `icons/adwaita-icons.ttf`), which is produced
  by a build script and should never be edited by hand.

## Repository structure

```
.
├── assets/
│   ├── icon.svg              Extension icon, editable source of truth
│   └── icon.png              Rasterised marketplace icon (512x512, generated)
├── icons/
│   ├── adwaita.json          Product icon theme manifest
│   ├── adwaita-icons.ttf     COLRv1 icon font (generated by nanoemoji)
│   └── svg/                  Icon glyph sources, named by codepoint
├── src/
│   ├── adwaita.ts            libadwaita palette and semantic surface tokens
│   ├── color.ts              Colour maths: hex, oklab, contrast, mixing
│   ├── gtksourceview.ts      Minimal strict XML reader
│   ├── style-scheme.ts       Typed reader for GtkSourceView style schemes
│   ├── scopes.ts             GtkSourceView style name -> TextMate scope map
│   ├── syntax.ts             Builds tokenColors and semanticTokenColors
│   ├── workbench.ts          Derives semantic workbench tokens per variant
│   ├── workbench-colors.ts   Places tokens on VS Code colour keys
│   ├── themes.ts             Assembles the eight variants
│   ├── vscode-color-ids.json Colour keys registered by VS Code, for validation
│   ├── gtksourceview/        Vendored Adwaita and Adwaita-dark style schemes
│   └── default-themes/       VS Code built-in token colours for the variants
├── scripts/
│   ├── build.ts              Generates themes/ and validates icons/
│   ├── icon-support.ts       TTF cmap reader and icon theme validation
│   ├── validate.ts           Full project validation
│   ├── package.ts            VSIX packaging
│   └── update-gtksourceview.ts  Refreshes the vendored schemes from upstream
├── tests/                    Bun test suite
├── themes/                   Generated colour themes, committed to the repo
└── .github/                  CI, issue templates, PR template
```

## Prerequisites

| Tool                                                  | Version | Why                                              |
| ----------------------------------------------------- | ------- | ------------------------------------------------ |
| [Bun](https://bun.sh)                                 | 1.1+    | Runs the build scripts and the test suite        |
| Node.js                                               | 24+     | Only needed if you prefer running `tsc` directly |
| [nanoemoji](https://github.com/googlefonts/nanoemoji) | latest  | Only to rebuild the icon font                    |

Install dependencies with:

```bash
bun install
```

## Development workflow

```bash
bun run build        # regenerate themes/ and validate icons/
bun run test         # run the test suite
bun run typecheck    # tsc --noEmit
bun run lint         # Biome lint
bun run format       # Biome format --write
bun run validate     # manifest + themes + tokens + icons + contrast
bun run verify       # all of the above in one command
```

To see your changes in the editor, open the repository in VS Code or VSCodium
and press `F5`. That uses the `Launch Extension` configuration in
`.vscode/launch.json` and opens a new window with the theme loaded from the
working tree.

## Theme architecture

The build is a small pipeline. Each stage is a pure function, which is what makes
the output reproducible:

```
GtkSourceView XML  ─┐
                    ├─> style-scheme.ts ─> syntax.ts ─> tokenColors
libadwaita tokens  ─┤                                   + semanticTokenColors
                    └─> adwaita.ts ─> workbench.ts ─> semantic tokens
                                                  └─> workbench-colors.ts ─> colors
                                                                              │
                            themes.ts <───────────────────────────────────────┘
                                        │
                                   themes/*.json
```

Three independent choices define a variant: light or dark, Adwaita or default
syntax highlighting, and a neutral or colourful status bar. That is the
`itertools.product` of `THEME_VARIANTS` in `src/themes.ts`, giving eight files.

`src/workbench-colors.ts` is the **only** module that knows VS Code's colour key
vocabulary. Everything upstream of it speaks Adwaita. If you want to style a new
VS Code surface, add a line there; do not hardcode a hex value.

## Design token workflow

All colour decisions start in `src/adwaita.ts`. That file holds:

- `ADWAITA_PALETTE`, the shared named palette (`blue_1` .. `yellow_6`, `teal_*`,
  `violet_*`, `chameleon_3`, and so on).
- `ADWAITA_DARK_RAMP`, the one part of the palette that GtkSourceView redefines
  per variant.
- `ADWAITA_SURFACES`, libadwaita's semantic tokens for light and dark.

`src/workbench.ts` turns those into a `WorkbenchTokens` object with semantic
names such as `editorBg`, `sidebarBg`, `overlayBg`, `fgMuted`, `border` and
`gitAdded`. **Add a token there, not a colour key.** If two variants need to
differ, they should differ in the token values, never in the placement logic.

To refresh the token values from a newer libadwaita, extract them from the
installed library, for example:

```bash
python3 - <<'PY'
import re
data = open('/usr/lib64/libadwaita-1.so','rb').read()
i = data.find(b'@define-color blue_1')
chunk = data[i:i+22000].decode('latin1','replace')
for line in chunk.split('\n'):
    s = line.strip()
    if s.startswith('@define-color') or s.startswith('@media'):
        print(s[:170])
PY
```

Foregrounds in libadwaita are a colour plus an opacity
(`window_fg_color: RGB(0 0 6 / 80%)`). VS Code colour keys take no independent
text alpha, so `ADWAITA_SURFACES` stores each foreground already composited over
its own surface. Use `mix(surface, foregroundBase, opacity)` from
`src/color.ts` to compute one.

## Light and dark conventions

Both variants are polished independently. Do not derive one from the other, and
do not invert.

- Surfaces come from libadwaita. In dark style the editor (`view`) is darker than
  the chrome, which is the upstream signal for a recessed content area.
- Borders are a tint of the foreground over the surface, matching how libadwaita
  derives `*_border_color`. Use `tint(surface, fg, amount)`.
- **No accent outlines on selection.** libadwaita signals the selected tab, list
  row or view with surface tone and a filled background, never with an accent
  coloured border. `tab.activeBorder`, `tab.activeBorderTop`,
  `tab.selectedBorderTop` and `activityBar.activeBorder` are therefore
  transparent. Accent is reserved for things that genuinely are accent: buttons,
  badges, progress, focus rings and links.
- Accents come from the palette. The default accent is `blue_3`; `accentColor` is
  derived from it with the same oklab transform libadwaita uses.
- `bun run validate` checks ten foreground/background pairs per variant against
  WCAG AA. Line numbers are held to 3:1 because they are non-essential text;
  the accent foreground is held to 3:1 because that is libadwaita's own contrast
  for white on `blue_3`. Everything else must clear 4.5:1.

## Syntax highlighting conventions

`src/scopes.ts` maps GtkSourceView style names to TextMate scope selectors. It is
hand curated, and the comments in it explain the non-obvious choices.

Rules:

- **Generic first, language specific later.** TextMate applies rules in order and
  a later rule wins, so `def:*` entries come before `css:*`, `rust:*` and friends.
- **No duplicate selectors.** A test enforces this. Prefix overlaps are fine and
  intentional, for example `markup.deleted` in `def:deletion` and
  `markup.deleted.diff` in `diff:removed-line`.
- **Do not invent scopes.** Find the real scope with **Developer: Inspect Editor
  Tokens and Scopes** in VS Code before adding a selector.
- **Prefer less colour.** The upstream project deliberately leaves function names
  and operators uncoloured; keep that bias.

To refresh the vendored schemes:

```bash
bun run update:gtksourceview
bun run build:themes
```

If upstream renames or removes a style, the build fails with a message naming the
style. Update `src/scopes.ts` accordingly. The build also reports scheme styles
that the scope map does not reference; editor-only styles such as `cursor`,
`line-numbers` and `search-match` are expected to be unmapped because VS Code
exposes those as workbench colours instead.

`src/syntax.ts` additionally builds `semanticTokenColors` so language servers
colour code the same way the TextMate rules do. Every entry points at the
Adwaita style that the equivalent TextMate rule uses, which is what keeps the two
paths visually identical.

## Product icon workflow

The icon font is compiled by [nanoemoji](https://github.com/googlefonts/nanoemoji),
which is the maintained tool for COLRv1 colour fonts. Reimplementing it in
TypeScript would be a large amount of fragile code for no benefit, so the build
validates and reports instead, and the font build is a documented separate step.

To add an icon:

1. Obtain an SVG from the
   [Icon Library](https://flathub.org/apps/details/org.gnome.design.IconLibrary)
   app.
2. Name it after its codepoint in lowercase hex, for example `ea0e.svg`, and put
   it in `icons/svg/`.
3. Open it in a text editor, replace the hardcoded colour with `currentColor`,
   and add `style="transform:scale(0.8)translate(2,2)"`.
4. Edit the icon if needed.
5. Add an entry to `iconDefinitions` in `icons/adwaita.json`.
6. Rebuild the font:

   ```bash
   mkdir -p build && cp -r icons/svg build/svg
   nanoemoji --color_format glyf_colr_1 --family adwaita-icons \
     --output_file icons/adwaita-icons.ttf build/svg/*.svg
   rm -rf build
   ```

7. Run `bun run validate`. It reads the font's `cmap` table and fails if any
   icon points at a codepoint the font does not contain.

Two constraints worth knowing:

- `U+EB94` is reserved for the menu bar icon. VS Code's menu bar CSS hardcodes
  that codepoint.
- nanoemoji derives codepoints from the SVG file names, so the file name and the
  `fontCharacter` in the manifest must agree.

## Validation

`bun run validate` checks:

- **Manifest**: required fields, extension name, licence, publisher, version
  format, URLs not pointing at upstream, icon exists and is a PNG, exactly eight
  themes with both `vs` and `vs-dark`, one product icon theme, all contributed
  paths exist.
- **Themes**: `$schema`, `name`, `type` matching the variant, colour values are
  well formed, colour keys are in `src/vscode-color-ids.json`, `semanticHighlighting`
  is enabled, every token rule has a scope and valid settings, no unsupported
  `fontStyle` values, no duplicate scopes in Adwaita variants.
- **Tokens**: every palette value is a valid colour, and ten contrast pairs per
  variant meet their thresholds.
- **Icons**: manifest parses, font sources exist and are sfnt fonts, every
  codepoint resolves, no two icons share a codepoint, every referenced SVG exists.

`src/vscode-color-ids.json` is the list of colour keys registered by VS Code,
extracted from a specific VSCodium release. If you add a colour key that VS Code
has since added, update that file and note the version in its `source` field.

## Formatting and type checking

[Biome](https://biomejs.dev) handles both formatting and linting:

```bash
bun run format       # rewrite
bun run format:check # check only, what CI runs
bun run lint
```

TypeScript runs in strict mode with `noUncheckedIndexedAccess`,
`exactOptionalPropertyTypes` and `verbatimModuleSyntax`. Run `bun run typecheck`
before committing.

Generated JSON under `themes/`, `src/default-themes/` and
`src/vscode-color-ids.json` is excluded from Biome, because its formatting is
owned by the generator.

## Build and packaging

```bash
bun run build     # generate themes/ and validate icons/
bun run package   # produce dist/*.vsix with @vscode/vsce
```

`.vscodeignore` keeps the VSIX to what the editor needs: the eight themes, the
product icon manifest and font, and the extension icon. Sources, scripts, tests,
documentation and CI configuration are excluded.

### Before you publish

`publisher` in `package.json` is a placeholder. Replace it with the real
namespace, or pass one through the environment:

```bash
VSC_ADWAITA_PUBLISHER=your-namespace bun run package
```

Publishing itself needs a registered publisher and a token, neither of which
lives in this repository. Nothing in the repository publishes automatically.

## Testing

Tests use Bun's built-in runner:

```bash
bun test tests/
```

Three files:

- `tests/color.test.ts` covers the colour maths, including the oklab round trip
  and the libadwaita accent derivation.
- `tests/style-scheme.test.ts` covers the XML reader, the style scheme reader,
  the vendored schemes, and the invariants of the scope map.
- `tests/themes.test.ts` covers the variant matrix, theme assembly, the surface
  hierarchy, border derivation, and the syntax colour rules.

Add a test whenever you change token derivation, scope mapping, or variant
assembly. A theme regression is invisible until someone looks at a screenshot.

## Visual QA

Theme changes are impossible to review from a diff alone. The `samples/`
directory holds one file per language family plus dedicated files for diff and
Markdown, each chosen to exercise the scopes the theme styles separately.

To check a change:

1. Run `bun run build:themes`.
2. Open a file from `samples/` in VS Code or VSCodium and press `F5`.
3. Switch between **Adwaita Dark** and **Adwaita Light**.
4. Compare against the checklist in `samples/README.md`.

Screenshots of both variants are the most useful thing to attach to a design PR.
The `samples/` directory is excluded from the published extension.

## Pull request expectations

- Keep the diff focused. One concern per PR.
- Run `bun run verify` and paste the result, or say which checks you could not
  run and why.
- If you changed a token, say which upstream value it now matches.
- If you added a colour key, confirm it is in `src/vscode-color-ids.json`.
- Do not edit files under `themes/` by hand. Change the generator.
- Do not reformat files you did not otherwise touch.

## Bug reporting

Open an issue and include:

- the theme variant you are using,
- the editor and version (VS Code, VSCodium, or other Code - OSS build),
- the language and, if it is a syntax problem, the scope from
  **Developer: Inspect Editor Tokens and Scopes**,
- a screenshot of both light and dark if the problem is visual.

For syntax highlighting problems, please include the GtkSourceView style you
expected, if you know it.

## Design contribution guidelines

- Ground every colour in libadwaita. If you cannot point at a token, explain why
  a new value is needed.
- Prefer a derived value over a hardcoded one. `tint`, `mix`, `withAlpha` and
  `deriveAccentColor` exist for this.
- Keep both variants coherent. A change that only works in one variant is usually
  a token problem, not a placement problem.
- Aim for WCAG AA. If you cannot reach it, say so in the PR and explain the
  trade-off.
- Avoid adding borders. libadwaita separates surfaces with tone, not lines.
- Do not add saturation. Adwaita is deliberately quiet.

## Release workflow

1. Update `CHANGELOG.md`.
2. Bump `version` in `package.json`.
3. Run `bun run verify`.
4. Commit, and open a PR.
5. Tag the release: `git tag v1.2.3 && git push --tags`.
6. The `release` workflow builds the VSIX on the tag and attaches it to the
   GitHub release.
7. Publishing to the Visual Studio Marketplace and Open VSX is a manual step and
   needs credentials that are not stored in this repository.

The workflows never publish on a push to `main`. Publishing is tag triggered and,
for the marketplaces, requires an explicit manual trigger.
